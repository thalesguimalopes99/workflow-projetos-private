Pessoal, existe uma feature no Superbase chamada Security Advisor, ou seja, um conselheiro de segurança para o teu banco de dados. Então repare que eu tenho uma tabela aqui com um cadeado aberto. Ele está indicando que essa view foi criada com Security Definer. O que isso significa? Eu até comentei em aulas anteriores onde eu mostro aquele slide. Quando eu crio uma View com o Security Definer, quer dizer que quem for acessar os dados da View vai acessar com os privilégios de quem criou a View e não os privilégios da própria pessoa. Ou seja, eu vou ter privilégios do Postgres que tem acesso a todas as tabelas. Isso é péssimo para a segurança. O ideal é que quem fosse acessar a View, essa análise... fosse feita com os privilégios da pessoa, ok? Ou seja, Security Invoker. Vai verificar o nível de segurança da pessoa que está invocando a View, ok? Então, para corrigir isso, repare que, além de mostrar visualmente através de um cadeado, ele também mostra aqui no Advisor, no seu conselheiro. O Security Advisor, ele indica que existe um erro de segurança, e a hora que você clica nesse erro, ele mostra Security Definer View, Entidade é o nome da sua View, qual que é o problema? a View está definida como Secure Definer. Descrição detecta que a View foi definida com a propriedade Secure Definer. Essa View força as permissões do Postgres para RLS com as permissões do criador, ao invés das permissões de quem está chamando, quem está fazendo a query da View. Então, para resolver isso, você pode vir aqui em ViewDocs. E o mais legal é que, na hora que você abre essa página, repare que ela é dinâmica. Ela tem vários motivos de segurança que você pode melhorar a tua aplicação. É óbvio que o Advisor vai indicar exatamente qual é o problema. Mas se você quiser melhorar a segurança do teu banco, você já pode implementar isso aqui de antemão. Então, aqui na aba Security Definer, ele explica qual é o problema, dá a solução através de código e a gente pode implementar. Então, eu vou corrigir aquela tabela. Como é que eu faço isso? Eu volto aqui no meu banco, aliás, aquela View. Eu clico aqui, venho na definição dela, copio toda a definição, vou lá no meu GPT, e aqui eu vou solicitar o seguinte. Deixa eu só voltar na documentação. Ele fala como habilitar o Security Invoker. Eu clico aqui e falo o seguinte. Apague a View abaixo e recrie. com o mesmo nome, porém, agora, utilizando security invoker igual a true. Então, eu venho aqui, colo a referência da documentação, e mando para o GPT. Vamos aguardar ele criar. Ele dá um drop view para apagar a view. Depois, ele cria já com security invoker igual a true. Então, onde que eu implemento isso? Eu volto lá no meu SQL Esther. Deixa eu limpar o código aqui. E vou copiar tudo isso aqui. Ctrl A, Ctrl C, para o que dá um run. Ele só dá um aviso aqui que quando você está apagando uma tabela, isso é uma operação destrutiva e isso pode impactar o teu banco. No caso, eu sei exatamente o que eu estou fazendo, então vou clicar em Run This Query. Pronto. Agora, se eu voltar lá em Table Editor, repare que não tem mais aquele cadeado indicando que a View está aberta. Ou seja, eu acabei de proteger a View. Aqui no Advisor, se eu der um rerun linter, ele vai rodar novamente e agora só vai indicar uma sugestão de melhoria de segurança para uma policy em outra tabela que não é a que a gente estava trabalhando. Mas repare que o erro agora sumiu, ok? Então, a mensagem principal desse vídeo é utilize o Security Advisor para aprender sobre segurança nas suas aplicações. Você pode consultar a documentação e entender cada um dos motivos que ele aponta aqui para melhorar tanto segurança... quanto o performance, aqui no outro Advisor de performance. Então, dentro do Spapase, é o teu melhor amigo aqui no teu projeto. Então, espero que vocês tenham gostado desse vídeo e te vejo na próxima aula. Até mais!
