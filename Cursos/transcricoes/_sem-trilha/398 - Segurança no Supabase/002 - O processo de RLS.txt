Agora alguns pontos de atenção. Quem tem a política de segurança é a tabela. Ou seja, se eu utilizar uma view para acessar essa tabela, essa view, por padrão, vai fazer um bypass em todas essas regras. Ou seja, ela não vai respeitar regra nenhuma de policy. Então, ela vai conseguir acesso direto. Para a minha tabela, isso é péssimo. Por que acontece isso? Tem uma definição. As views ignoram o RLS por padrão, porque geralmente são criadas com o usuário Postgres. Este é um recurso do Postgres que cria automaticamente views com o Security Definer. Ou seja, vai obedecer as regras de quem criou a view, e não de quem está tentando acessar. Então, para corrigir isso, você tem que criar uma view... informando esse campo aqui, security invoker true, ou seja, a view vai respeitar o acesso de quem está invocando ela, ou seja, quem está solicitando a informação. Então, aí sim, na hora de criar a view, se você informar esse campo aqui, ele vai passar por todas essas barreiras aqui até chegar na tabela. Bom, eu mencionei a respeito das chaves, e muita gente tem dúvida se é seguro, se não é, como é que funciona. Então, para acessar... um role autenticado, eu preciso da API Key e o User Key. Aí o pessoal pergunta, mas é seguro esse User Key, não é? Essa chave é uma chave do usuário, não é uma chave tua. Então, por exemplo, imagine que você está usando uma API Key lá da OpenAI. Essas chaves não podem ser exibidas do lado do cliente. Imagine que você tem uma chave que você está pagando para ela ser usada e você coloca lá no front-end. Isso é inadmissível, porque o usuário vai poder ter acesso a essa chave e poder usar a ferramenta, sendo que você vai pagar por ela. Então, chaves como a API Key da OpenAI, você não pode utilizar de forma nenhuma no front-end. Só que a User Key é uma chave do usuário. Então, ele que vai usar essa chave para poder acessar os recursos. É lógico que a tua aplicação tem que garantir que essa chave não vai vazar. Isso é feito da forma como você implementar. Se você usar o Flutter Flow, por exemplo, o Flutter Flow tem os mecanismos dele para proteger essa chave de modo que ela não seja exposta, não seja roubada, que outra pessoa não consiga se passar por você usando o token autenticado, entendeu? Então, eu coloquei aqui na definição o seguinte, essa chave é do usuário e é segura para uso em navegador desde que algumas medidas sejam tomadas. Ou seja, o protocolo onde essa comunicação é feita entre você e a aplicação tem que ser um protocolo seguro, você tem que ter habilitado RLS e o armazenamento desse token JWT tem que ser feito de forma segura. Existem algumas formas que eu coloquei aqui, pode ser armazenada em memória, local storage ou através de cookies. utiliza o pacote Superbase Flutter, que faz o armazenamento via Local Storage. É lógico, as três formas são seguras, porém existem níveis de segurança entre elas, tem vantagens e desvantagens a cada uma. O que eu quero dizer é que você consegue sim utilizar essa chave de forma segura dentro da tua aplicação e o Flutter Flow faz essa gestão de tokens para você. E por último, a gente tem a Service Role Key. Essa Service Roll Key é uma chave que você também nunca pode expor lá no teu front-end, porque ela é uma chave que faz o bypass de todo o RLS, ou seja, ela faz esse caminho aqui. Ela não passa por política nenhuma. Então, você não pode exibir essa chave no teu front-end, ok? Essa chave geralmente é usada para serviços administrativos, que vamos supor que eu quero fazer um upload em massa de dados no banco, eu posso usar essa chave para dar um bypass em todas as tabelas e só inserir informação lá, entendeu? Então, é... fica claro o perigo de expor essa chave no front-end. Então, de forma bem resumida, API Key é pública, pode ser usada no front-end desde que você tenha RLS. User Key não é pública, mas ela pode ser usada no front-end desde que armazenada de forma segura, que tenha RLS e que seja transitada utilizando um protocolo como HTTPS.
